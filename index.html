How to Use This Runbook

Every command block below has a Copy button in the top-right corner — click it to copy that block straight to your clipboard, then paste into your terminal or PowerShell session on the client's machine. This works fully offline; no internet connection is required to use this page.

  • Replace any placeholder in angle brackets, e.g. <manager-ip>, with the actual value for the client's environment before running.
  • Run steps in order — later steps assume earlier ones completed successfully.
  • Commands prefixed with sudo require root/administrator privileges.

2. Server Preparation

2.1 Update the System & Install Dependencies

sudo apt update && sudo apt upgrade -y
sudo apt install -y curl apt-transport-https unzip wget libcap2-bin jq

2.2 Apply Kernel Tuning (required for the Wazuh Indexer)

cat << 'EOF' | sudo tee /etc/sysctl.d/99-wazuh.conf
vm.max_map_count=262144
net.core.somaxconn=65535
net.ipv4.tcp_max_syn_backlog=65535
EOF
sudo sysctl --system

2.3 Open Required Firewall Ports (UFW)

sudo ufw allow 1514/tcp
sudo ufw allow 1515/tcp
sudo ufw allow 1516/tcp
sudo ufw allow 55000/tcp
sudo ufw allow 9200/tcp
sudo ufw allow 443/tcp
sudo ufw allow 514/udp
sudo ufw enable

3. Install Wazuh Manager, Indexer & Dashboard

The official installation assistant deploys all three central components on this single Ubuntu server in one pass.

3.1 Download the Installer

cd /root
curl -sO https://packages.wazuh.com/4.14/wazuh-install.sh
curl -sO https://packages.wazuh.com/4.14/config.yml

3.2 Run the All-in-One Installer

sudo bash wazuh-install.sh -a
Note: This takes 10-15 minutes. At the end it prints the dashboard URL and a one-time admin password — copy it immediately, it is not shown again on screen.

3.3 Retrieve the Admin Password (if missed)

sudo tar -O -xvf wazuh-install-files.tar wazuh-install-files/wazuh-passwords.txt

3.4 Change the Default Admin Password

sudo /usr/share/wazuh-indexer/plugins/opensearch-security/tools/wazuh-passwords-tool.sh \
  -u admin -p 'ReplaceWithAStrongPassword!2026'

3.5 Verify All Services Are Running

sudo systemctl status wazuh-manager
sudo systemctl status wazuh-indexer
sudo systemctl status wazuh-dashboard
sudo systemctl status filebeat

3.6 Access the Dashboard

https://<wazuh-server-ip>
# Login: admin
# Password: <the password set in step 3.4>

4. Agent Enrollment — Forward Asset Logs to the Manager

Run the relevant block below on each in-scope asset. Replace <manager-ip> with the Wazuh server's IP address in every command.

4.1 Ubuntu / Debian Servers

Applies to all Ubuntu-based assets (application servers, ERP, object storage, container hosts, backup server, Zabbix host, etc.)

curl -so wazuh-agent.deb https://packages.wazuh.com/4.x/apt/pool/main/w/wazuh-agent/wazuh-agent_4.14.0-1_amd64.deb
sudo WAZUH_MANAGER='<manager-ip>' dpkg -i ./wazuh-agent.deb
sudo systemctl daemon-reload
sudo systemctl enable wazuh-agent
sudo systemctl start wazuh-agent

4.2 RHEL / Oracle Linux Servers

Applies to RHEL 7, RHEL 9, and Oracle Linux assets (core banking app, core DB, reverse proxy, ticketing system, etc.)

curl -o wazuh-agent.rpm https://packages.wazuh.com/4.x/yum/wazuh-agent-4.14.0-1.x86_64.rpm
sudo WAZUH_MANAGER='<manager-ip>' rpm -ihv wazuh-agent.rpm
sudo systemctl daemon-reload
sudo systemctl enable wazuh-agent
sudo systemctl start wazuh-agent
Note: RHEL 7 is past its standard support window — confirm Extended Life Cycle Support coverage with the client, and flag these hosts for OS upgrade planning separately from this Wazuh rollout.

4.3 Windows Server Hosts

Applies to database servers, IIS/web servers, the domain controller, and other Windows Server 2022 assets. Run in an elevated PowerShell prompt.

Invoke-WebRequest -Uri https://packages.wazuh.com/4.x/windows/wazuh-agent-4.14.0-1.msi -OutFile $env:tmp\wazuh-agent.msi
msiexec.exe /i $env:tmp\wazuh-agent.msi /q WAZUH_MANAGER='<manager-ip>'
NET START WazuhSvc
Note: Deploy Sysmon separately on these hosts (Section 5) so richer process, registry, and network telemetry feeds into the same agent. Prioritize DC01 (domain controller) and both database servers.

4.4 Verify Agent Connectivity (run on the manager)

sudo /var/ossec/bin/agent_control -l

Each enrolled asset should show status Active within 1-2 minutes of the agent service starting. This can also be confirmed visually under Agents in the Wazuh dashboard.

5. Sysmon Installation & Integration (Windows Hosts)

Sysmon logs detailed process creation, network connection, file, and registry activity to the Windows Event Log. Wazuh reads this log channel directly, giving far richer detection value than the default Windows Event Log alone. Install on every Windows Server 2022 asset from Section 4.3 — especially DC01 and both database servers.

5.1 Download Sysmon and a Community Configuration

Run in an elevated PowerShell prompt. This uses the widely-used SwiftOnSecurity baseline configuration.

Invoke-WebRequest -Uri https://download.sysinternals.com/files/Sysmon.zip -OutFile $env:tmp\Sysmon.zip
Expand-Archive -Path $env:tmp\Sysmon.zip -DestinationPath $env:tmp\Sysmon -Force
Invoke-WebRequest -Uri https://raw.githubusercontent.com/SwiftOnSecurity/sysmon-config/master/sysmonconfig-export.xml -OutFile $env:tmp\sysmonconfig.xml

5.2 Install Sysmon with the Configuration

cd $env:tmp\Sysmon
.\Sysmon64.exe -accepteula -i $env:tmp\sysmonconfig.xml
Note: On a system that already has Sysmon installed, use -c instead of -i to update the configuration without reinstalling.

5.3 Verify Sysmon Is Running

Get-Service Sysmon64
Get-WinEvent -LogName 'Microsoft-Windows-Sysmon/Operational' -MaxEvents 5

5.4 Point the Wazuh Agent at the Sysmon Log Channel

Edit the Wazuh agent configuration file on the Windows host:

C:\Program Files (x86)\ossec-agent\ossec.conf

Add the following block inside <ossec_config>, alongside any existing <localfile> entries:

<localfile>
  <location>Microsoft-Windows-Sysmon/Operational</location>
  <log_format>eventchannel</log_format>
</localfile>

5.5 Restart the Wazuh Agent to Apply the Change

Restart-Service -Name WazuhSvc

5.6 Confirm Sysmon Events Are Reaching the Manager

Wazuh ships built-in decoders and rules for Sysmon (rule group sysmon) enabled by default — no custom ruleset needed. On the manager:

sudo tail -f /var/ossec/logs/alerts/alerts.log | grep -i sysmon

Or in the dashboard: filter Agents by the Windows hostname and confirm events with rule.groups containing sysmon are arriving.

5.7 Recommended Sysmon Priorities for This Environment

  • DC01.example.local — process creation and network connection events are the highest-value signal, since this host is the identity backbone.
  • DB-Server-01 / DB-Server-02 — watch for unexpected process creation under the SQL Server service account, and unusual outbound connections.
  • IIS hosts (Web-Portal-01, Web-Services-01, Web-Staging-01) — watch for child processes spawned by w3wp.exe, a common web-shell indicator.
  • Revisit the config after 2 weeks of data and tune out noisy events before enabling active response tied to Sysmon-sourced rules.

6. Agentless Devices — Syslog Forwarding

The F5 BIG-IP WAF pair and the FreeBSD OpenVPN gateway cannot run a native Wazuh agent. These forward logs via syslog instead. This section covers both sides: the manager-side listener, and the configuration required on each agentless device itself.

6.1 Configure the Manager to Accept Syslog

Add the following block inside <ossec_config> in /var/ossec/etc/ossec.conf:

<ossec_config>
  <remote>
    <connection>syslog</connection>
    <port>514</port>
    <protocol>udp</protocol>
    <allowed-ips>,,</allowed-ips>
  </remote>
</ossec_config>
sudo systemctl restart wazuh-manager

6.2 F5 BIG-IP WAF — Device-Side Configuration (Both Nodes)

System-level syslog (via TMSH):

tmsh modify sys syslog remote-servers add { wazuh-manager { host <manager-ip> remote-port 514 } }
tmsh save sys config

ASM/WAF violation logging requires its own logging profile — system syslog does not include security policy violations automatically:

  • Security → Event Logs → Logging Profiles → Create new profile, Type: Application Security.
  • Under Remote Storage: set type Remote, protocol TCP or UDP, target <manager-ip>:514, format CEF, Splunk, or syslog.
  • Attach this logging profile to each virtual server / security policy on both the active and standby WAF nodes.

Verify logs are being generated locally before troubleshooting the network path:

tmsh show sys log-config
tail -f /var/log/asm

6.3 FreeBSD OpenVPN Gateway — Device-Side Configuration

Point syslogd at the Wazuh manager — edit /etc/syslog.conf:

*.*   @<manager-ip>:514
sudo service syslogd restart

Confirm OpenVPN itself logs through syslog rather than only to a flat file — check the server config (e.g. /usr/local/etc/openvpn/server.conf) includes:

syslog openvpn
verb 3

Test forwarding end to end:

logger -p auth.info "wazuh-syslog-test from OpenVPN gateway"

Then, on the Wazuh manager, confirm it arrived:

sudo tail -f /var/log/syslog | grep wazuh-syslog-test

6.4 Firewall Rules for Agentless Devices

Both agentless devices need outbound UDP/TCP 514 permitted toward the Wazuh manager, and the manager needs inbound 514 open from their IPs specifically (already covered in Section 1.2).

  • F5 BIG-IP: if a self-IP port lockdown or packet filter is configured (Network → Self IPs → Port Lockdown), explicitly allow port 514 outbound to the manager, or set the relevant self-IP's port lockdown to Allow Default plus the syslog port.
  • FreeBSD OpenVPN gateway: if pf or ipfw is enabled, add an explicit rule permitting outbound UDP 514 to the manager IP, e.g. (pf): pass out on $ext_if proto udp from any to <manager-ip> port 514.
  • Wazuh manager (Ubuntu/UFW): scope inbound 514/udp to just these device IPs rather than leaving it open broadly, since this is Critical-tier traffic:
sudo ufw allow from  to any port 514 proto udp
sudo ufw allow from  to any port 514 proto udp
sudo ufw allow from  to any port 514 proto udp

6.5 Installing rsyslog as a Forwarder on a Linux Server (if firewall/relay needed)

If a Linux host needs to relay syslog to the Wazuh manager (for example, a jump host relaying for devices that can't reach the manager directly due to firewall segmentation), install and configure rsyslog as follows.

Ubuntu / Debian:

sudo apt update
sudo apt install -y rsyslog

RHEL / Oracle Linux:

sudo yum install -y rsyslog

Enable and start the service:

sudo systemctl enable rsyslog
sudo systemctl start rsyslog

Configure forwarding — create /etc/rsyslog.d/60-wazuh-forward.conf:

# UDP forwarding
*.* @<manager-ip>:514

# or TCP forwarding (more reliable, note the double @)
*.* @@<manager-ip>:514

Restart rsyslog to apply:

sudo systemctl restart rsyslog

Open the firewall for outbound syslog:

# UFW (Ubuntu)
sudo ufw allow out 514/udp

# firewalld (RHEL / Oracle Linux)
sudo firewall-cmd --permanent --add-port=514/udp
sudo firewall-cmd --reload

Test the forwarder:

logger "wazuh-syslog-test from $(hostname)"

Then confirm receipt on the Wazuh manager the same way as Section 6.3.

7. Post-Installation Checklist

  • Admin password changed from the auto-generated default.
  • Dashboard reachable over HTTPS from the client's internal network.
  • All target agents show Active status in Agents view.
  • Sysmon installed and reporting on all Windows Server 2022 assets, prioritizing DC01 and both database servers.
  • Syslog test event received from each of the 3 agentless devices, using the device-side steps in Section 6.
  • Firewall rules confirmed open — both inbound on the manager and outbound on each agentless device.
  • Firewall rules confirmed open between the Wazuh server and every asset segment.
  • Admin password and any generated certificates stored securely (password manager / vault), not left on disk.
